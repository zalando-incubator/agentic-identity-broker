# Contract: Upstream Token Endpoint Requests

**Feature**: `042-thirdparty-public-pkce` | **Date**: 2026-09-10
**Implemented by**: `internal/domain/oauth2session/service.go`
**Depends on**: [research.md](../research.md) decision D1

This is the outbound HTTP contract between the broker and a third-party provider. It is an external
interface: providers observe it, and E2E tests assert on it byte by byte. Both modes are specified
here so that "unchanged for confidential services" (FR-017) is a checkable statement rather than an
intention.

Exactly two operations transmit a third-party client credential upstream — the authorization-code
exchange and the refresh — and no other component may send one (FR-029).

---

## 1. Authorization redirect — identical in both modes

**Built by**: `InitiateOAuth2Flow` (`internal/domain/oauth2session/service.go:383-432`)

```
GET {authorize_endpoint}
  ?response_type=code
  &client_id={client_id}
  &redirect_uri={callback_url}
  &scope={space-delimited scopes}
  &state={JWE state token}
  &code_challenge={BASE64URL(SHA256(verifier))}
  &code_challenge_method=S256
  [&{provider authorization params}]
```

- `code_challenge` and `code_challenge_method=S256` are present on **every** third-party
  authorization request, public and confidential alike. This is not configurable, weakenable, or
  disableable (FR-010, SR-001). `plain` is never used.
- The verifier is generated by `oauth2.GenerateVerifier()` and sealed into the JWE state token; it
  is never logged, returned, or persisted beyond that token's TTL (FR-011, SR-002).
- Provider authorization parameters are applied after `AuthCodeURL`, filtered against the reserved
  name list (FR-018).

**No change is made to this path.** It is specified here because it is now a hard invariant that the
public-client work must not weaken.

## 2. Authorization-code exchange

**Built by**: `buildOAuth2Config` (`:287-314`) and `exchangeCodeWithRetry` (`:317-364`), via
`golang.org/x/oauth2` `Config.Exchange`.

### 2.1 Confidential service — unchanged, byte for byte

`oauth2.Config.ClientSecret` holds the decrypted secret and `Endpoint.AuthStyle` is left at its zero
value, `AuthStyleAutoDetect`. The library therefore probes: it first sends the credential in an
`Authorization: Basic` header and, on error, retries once with the credential in the body. Whichever
style succeeds is cached on that `Config`.

```
POST {token_endpoint}
Content-Type: application/x-www-form-urlencoded
Authorization: Basic base64(urlencode(client_id):urlencode(client_secret))    # AutoDetect, first attempt

grant_type=authorization_code&code={code}&redirect_uri={callback}&code_verifier={verifier}[&{params}]
```

This is exactly today's behaviour and MUST NOT change (FR-017, SC-004).

### 2.2 Public service

`ClientSecret` is empty and `Endpoint.AuthStyle` is pinned to `oauth2.AuthStyleInParams`.

```
POST {token_endpoint}
Content-Type: application/x-www-form-urlencoded
                                                    # NO Authorization header of any kind

grant_type=authorization_code&code={code}&redirect_uri={callback}&client_id={client_id}&code_verifier={verifier}[&{params}]
```

Guaranteed by the library implementation
(`golang.org/x/oauth2@v0.36.0/internal/token.go:186-205`): under `AuthStyleInParams`, `client_id` is
set only when non-empty, `client_secret` is set only when non-empty, and `SetBasicAuth` is reached
only under `AuthStyleInHeader`.

**No probing occurs.** `RetrieveToken` (`token.go:215-224`) probes only when the style is
`AuthStyleUnknown`; pinning `InParams` disables the header-first attempt and the credentialed
fallback entirely (FR-015, SR-005).

### 2.3 Retries

`exchangeCodeWithRetry` receives an already-built `*oauth2.Config` and reuses it across up to
`MaxRetries` attempts with exponential backoff. The auth style is therefore fixed for the whole
sequence: no retry adds, removes, or alters a client credential (FR-016). No change to the retry
loop is required.

### 2.4 Cross-service isolation

`authStyleCache` is an unexported field on each `oauth2.Config` (`oauth2.go:61-63`), and a fresh
`Config` is built per operation. Two services sharing one upstream token endpoint — one public, one
confidential — cannot influence each other's auth style.

## 3. Refresh

**Built by**: `RefreshAccessToken` (`:653-738`). This is a hand-rolled form POST, not an
`oauth2.TokenSource`. There is no retry loop and no `Authorization` header on this path in either
mode.

### 3.1 Confidential service — unchanged

```
POST {token_endpoint}
Content-Type: application/x-www-form-urlencoded
Accept: application/json

grant_type=refresh_token&refresh_token={token}&client_id={client_id}&client_secret={secret}[&{params}]
```

### 3.2 Public service

```
POST {token_endpoint}
Content-Type: application/x-www-form-urlencoded
Accept: application/json

grant_type=refresh_token&refresh_token={token}&client_id={client_id}[&{params}]
```

The sole difference is the omitted `client_secret` form value (FR-014). A failed refresh surfaces to
the caller; the broker never retries with a credential and never downgrades the session
(FR-015, SR-005, User Story 3 scenario 4).

### 3.3 RFC 8693 token exchange

`tokenexchange.Service` calls `GetValidAccessToken` (`internal/domain/tokenexchange/service.go:308`),
which transparently refreshes an expired third-party token through the path above. It therefore
inherits public-client behaviour with no separate work and no separate contract.

---

## 4. Prohibited for public services (SR-003)

A public-client token request MUST NOT carry credential material by **any** channel:

| Channel | Prohibited form |
|---|---|
| Request body | `client_secret` with any value, including `""` |
| `Authorization` header | `Basic`, including an empty password (`base64("client_id:")`), or any other scheme |
| Query string | `client_secret` or any credential parameter |

Provider authorization parameters cannot reintroduce a credential: `client_id`, `client_secret`,
`grant_type`, `refresh_token`, the redirect/state/code names, and the PKCE names are all rejected as
reserved at registration time (`internal/domain/model/thirdparty_oauth2_provider.go:34-39`,
case-insensitive).

## 5. Test double conformance

`tests/e2e/helpers/mock_upstream.go` gains an opt-in strict public-client mode (default off, so
existing tests are unaffected):

| Endpoint | Behaviour in strict mode |
|---|---|
| `/authorize` | Records each S256 `code_challenge` against the authorization code it returns |
| `/token` | Returns `401 invalid_client` if an `Authorization` header is present **or** a `client_secret` form value is present |
| `/token` | Returns `400 invalid_grant` if `code_verifier` does not `S256`-hash to the challenge associated with its authorization code |
| `/token` | Otherwise issues tokens as configured |

This makes SC-002 ("a provider that rejects any request carrying client credentials") and SC-003
("zero requests carrying credential material") observable rather than assumed. The existing capture
API — `GetLastRequest` (headers) and `GetLastBody` (parsed form) at `mock_upstream.go:168-182` — is
sufficient for absence assertions and is unchanged.
