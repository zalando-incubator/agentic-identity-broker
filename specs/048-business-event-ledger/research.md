# Business Event Ledger — Research

**Date**: 2026-09-26 | **Branch**: `048-business-event-ledger`

This document distinguishes observed repository behavior from the selected design. It does not claim that the ledger or its acceptance tests exist. All initial technical unknowns have a design decision below; deployment workload measurements are an implementation acceptance prerequisite, not fabricated research results.

## 1. Atomic recording and transaction ownership

**Evidence**: `internal/ports/storage.go` defines `OAuth2TransactionManager`; `internal/adapters/storage/postgres/oauth2_transaction.go:13-56` carries `sqlx.Tx` in context. Only OAuth2 repositories consistently use that executor. `internal/domain/oauth2server/fosite_storage.go:79-101` bridges Fosite transactions. `internal/adapters/storage/factory.go` supplies a no-op transaction manager for memory. Grants, agents, approvals, credentials, and signing keys also contain autonomous transactions or direct pool statements.

**Decision**: Generalize that existing protocol to `StorageTransactionManager`, its context key, and shared executor; migrate every caller and remove the OAuth2-specific name and memory no-op. Provide transaction ownership/join semantics: the outer domain operation owns commit; nested repository/Fosite scopes join but cannot commit it. Nested failure poisons the owning transaction. Do not introduce a second transaction stack. A callback helper may wrap Begin/Commit/Rollback, but it must use the same manager.

Domain services own the business transition and append its validated event before commit. Repository operations return the affected row/changed result, not an assumed success derived from an earlier read. Lock and reread before comparing mutable state. No-op returns, lost CAS attempts, existing pending approvals, and already-consumed approvals produce no success event. Extend all affected autonomous repository transactions to join the ambient executor, preserving existing stronger isolation/locking requirements. Fail if a nested operation requires stronger isolation than its owner provides rather than silently weakening it.

Local token providers must own an outer transaction across Fosite response population, event recording, and final commit; inner Fosite commit does not release the owner. Validation/replay detection that intentionally commits security revocations stays before the issuance-success scope: a failed token request is not permission to roll back security revocation. Explicitly separate those committed security outcomes from unsuccessful issuance. Third-party network calls and encryption preparation stay outside long-held database locks where possible; recheck mutable preconditions before applying prepared state. A committed refresh is a separate fact even if a later exchange fails.

**Alternatives considered**: Post-handler logging cannot be atomic. SQL triggers lack authoritative actor and outcome semantics. An outbox without joining business transactions does not fix atomicity. Wrapping every HTTP request indiscriminately would change independent failure-side effects and hold transactions across network calls.

## 2. Memory isolation

**Decision**: Replace the no-op with one adapter-wide transaction visibility gate plus a touched-record undo journal. An owning transaction holds the exclusive gate from begin through commit/rollback. Every standalone read/write participates in the gate; ambient operations use internal unlocked entry points rather than recursively acquiring it. Undo records contain only changed entries and secondary indexes; no whole-store snapshots. Return independent domain values so callers cannot mutate committed memory through retained pointers. Defer broadcasts and cache invalidation until the owning transaction commits.

Memory also uses a lifecycle barrier acquired before the visibility gate. Append/dispatch take it shared; erasure, retention and policy changes take it exclusive. This deliberately serializes memory erasure more broadly than PostgreSQL while preserving its observable contract. Dispatch claims an immutable event/reference under a short visibility-gate section, releases that gate during synchronous export while retaining lifecycle shared, then reacquires it briefly to acknowledge. Collector waits therefore do not monopolize the memory business-transaction gate; erasure still waits for the in-flight attempt.

**Rationale**: An undo journal alone exposes uncommitted changes and can overwrite a concurrent writer during rollback. Existing per-repository mutexes are insufficient for cross-repository atomicity.

**Alternatives considered**: Full-map copying adds history-proportional cost. A commit-only mutex fails isolation. Keeping no-op transactions violates FR-007.

## 3. Identity, schemas, and immutable type names

**Evidence**: `go.mod` pins google/uuid v1.6.0 and google/jsonschema-go v0.4.2 (currently indirect). ADR 013 requires generated named IDs. The Go module path is `github.com/agentic-identity-broker/agentic-identity-broker`. The hosting organization appears only in repository metadata (README badges, Dockerfile image labels, the git remote), and accepted ADR 030 keeps vendor-specific values out of public source. Constitution Principle IV binds APIs to the Zalando RESTful API and Event Guidelines, whose Rule 213 defines event type names as `<functional-name>.<event-name>`.

**Decision**: Add generated `id.BusinessEventID` using library UUIDv7 generation, without changing constructors for existing UUIDv4 entity IDs. Full event names are `agentic-identity-broker.<event-name>` per Zalando Rule 213, with hyphenated event names such as `grant-created` and `signing-key-promoted`; source is `urn:agentic-identity-broker:broker`. Neither is configurable. Source identifies the producer application, while existing OTLP Resource attributes identify deployment instances.

Use Draft 2020-12 schemas and promote the existing google/jsonschema-go dependency to direct. Compile/resolve once at startup through an embedded-only registry; reject network reference loading, unknown types, and invalid payloads. Publish the envelope, catalogue, and 28 closed per-type schemas under `api/events/v1/` before producer implementation. The reviewed designs are in `contracts/schemas/`. Optional field additions must preserve all previously valid records; incompatible meanings require a new event type. Schema `$id`s are URNs (`urn:agentic-identity-broker:events:v1:<name>`) with absolute URN `$ref`s resolved by the registry's offline loader; they identify resources and are never fetched.

Validate typed UUIDs, UTC instants, IPs, trace identifiers, and semantic field provenance in addition to JSON shape. The pinned validator ignores `format`; the contracts use patterns and domain parsers rather than assuming `format` is enforced. Error reporting must never echo rejected values.

**Alternatives considered**: UUIDv4 is not time ordered; a hand-written identifier/JSON-schema engine is unnecessary. A free-form data map or open additional properties makes accidental disclosure likely. General event ingestion is out of scope. A configurable namespace would give one meaning several names across deployments and break published schemas, investigation queries and consumer rules; deployment identity already lives in OTLP Resource attributes. A hosting-derived namespace such as `io.github.<organization>` or `com.<vendor>` ties permanent names to an organization that can change while published names cannot. Relative `$ref`s would need a hierarchical HTTPS base, which again implies an owned host.

**Primary documentation**: [google/jsonschema-go v0.4.2](https://github.com/google/jsonschema-go/blob/v0.4.2/jsonschema/doc.go), [UUID library](https://pkg.go.dev/github.com/google/uuid#NewV7).

## 4. Trusted attribution and credential exclusion

**Evidence**: `internal/domain/security/context.go:17-26` has trace, actor, calling peer, client IP and user agent, but no span ID. Its user-agent treatment is truncation, not credential removal. `internal/domain/tokenexchange/service.go:176-201` finalizes SecurityContext with the affected principal as Actor and the validated client assertion subject as CallingPeer. Therefore copying `SecurityContext.Actor` into the ledger caller field would misattribute delegation. The request middleware defers finalization for all POST `/oauth2/token` requests.

**Decision**: Add a domain event-context value assembled from authenticated results plus the existing capture. `subject` is the affected principal; the ledger actor is the verified initiating caller. For delegated exchange, use the verified calling peer as actor and the validated affected principal as `subject` and `actor.on_behalf_of`. Do not modify existing slog attribution. For gateway approvals retain authenticated gateway identity separately from agent and principal. Null identities are intentional; the anonymous sentinel is not a principal. Machine client-credentials issuance has null subject, not an agent UUID disguised as a user.

For impersonation, only a subject established by the accepted authorization/delegation path may become authoritative, including ADR 031's narrowly authorized unverified-subject mode; do not copy partially evaluated audit claims from rejected rules. Keep the independently verified client assertion identity as initiating caller. Optional `data.delegating_actor_id` on impersonation events preserves the verified actor-token identity when distinct from the client, without replacing the caller.

Capture the valid request span ID at the adapter boundary only when its trace ID equals the authoritative SecurityContext trace ID; otherwise omit it. Pass that scalar context into the domain rather than importing tracing infrastructure into the event model. Background work has a fixed system actor and no fabricated request identifiers.

Reasons come from fixed templates selected by safe outcome codes, never raw upstream errors. Type data is deliberately small: most success events need only envelope references; credential and key events retain safe resource IDs. Raw user-agent strings are not retained: a recognized product is normalized to one of the fixed family names in the schema; unrecognized content is omitted. IPs come from the existing trusted-proxy extraction and typed parsing. Optional opaque session correlations are copied only from established non-credential context; arbitrary request strings, tool names/arguments, payloads, URLs, claims, and credential hashes are not copied. Schema validity alone is not proof of safe provenance.

**Alternatives considered**: Regex token scrubbing or length truncation cannot recognize arbitrary opaque credentials. Serializing existing structs or AuditRecord wholesale can leak partially trusted identities and arbitrary strings. Omitting all known affected principals would defeat subject erasure.

## 5. Crash-safe telemetry without changing slog

**Evidence**: The current log provider uses `sdklog.NewBatchProcessor` (`internal/adapters/telemetry/provider.go:374-380`). The pinned SDK supports EventName, synchronous processor export, explicit provider attribute limits, and dropped-attribute counts. `Logger.Emit` does not return export success. ADR 011 requires app-owned providers and rejects a custom telemetry port.

**Decision**: Insert a payload-free pending-delivery reference in the same transaction as each event when copying is effectively enabled. A builder-owned worker scans references, reloads the retained event under the lifecycle/subject barrier, and emits using a separate non-global SDK LoggerProvider in the existing telemetry adapter. Use the same exporter configuration and Resource construction, but a separate exporter instance and synchronous result-capturing processor. It delegates to the SDK synchronous processor and records its error into a private per-call result holder; a missing callback, dropped attribute, cancellation, or error is not an acknowledgement. Delete the pending reference only after successful export and commit. Crash after export but before acknowledgement may duplicate the copy with the same event ID.

No BatchProcessor or payload queue exists on this ledger pipeline. Explicit provider attribute count/value-length limits are unlimited (`-1`) so SDK environment variables cannot silently truncate the envelope; closed schemas bound field names, arrays remain single attributes, and producer provenance controls values. Existing request limits remain in force. Do not silently shorten a required field. Exporter failure leaves the reference for a later bounded attempt and cannot undo a business commit. Provider initialization failure remains non-fatal to the durable ledger; pending references remain, with a credential-free warning, and initialization is retried by the worker. The worker stops before its provider/storage shutdown.

The effective copy switch is `telemetry.enabled && telemetry.logs.enabled && business_events.telemetry_copy_enabled`. Explicitly disabling any relevant switch pauses existing pending references and does not create references for occurrences during disablement; re-enabling resumes retained pre-disable pending work, not historical backfill. Retention and recording are never disabled with telemetry.

**Alternatives considered**: After-commit best effort contradicts the accepted clarification. Reusing the slog bridge cannot set the complete event contract reliably and risks changing old signals. A batch queue can retain an erased payload after deletion. An erasure epoch checked before an asynchronous send still has a race. Updating `emitted_at` on immutable ledger rows mixes delivery state with authority.

**Primary documentation**: [SDK synchronous processor](https://github.com/open-telemetry/opentelemetry-go/blob/sdk/log/v0.22.0/sdk/log/simple.go), [log record API](https://pkg.go.dev/go.opentelemetry.io/otel/log#Record), [SDK provider limits](https://pkg.go.dev/go.opentelemetry.io/otel/sdk/log#WithAttributeCountLimit).

## 6. Retention, partitions, and erasure barriers

**Evidence**: Accepted ADR 009 reserves schema-modification capabilities for migration workloads. The chart already uses a PostgreSQL-client maintenance image, migration service account, and separate migration Secret in `templates/job-migrate.yaml`. Latest local migration number is 032. PostgreSQL partitioned unique constraints must include the partition key.

**Decision**: Reserve migration 035 for ledger tables/functions and occurrence markers, because the unmerged `046-cimd-upstream-client` branch already holds 033 and 034; recheck allocation before implementation. Use six-hour UTC range partitions on `recorded_at`, paired with partitioned delivery-reference tables. Composite primary key `(recorded_at, id)`; trusted UUIDv7 generation supplies event identity. Mutations, CAS results and durable object markers establish occurrence uniqueness, not a partition-local event-type index. No event FK cascades from mutable business objects and no DEFAULT partition.

A separate chart CronJob runs every five minutes using the existing PostgreSQL client image and migration-owned credentials. It invokes a fixed SQL maintenance function supplied by migrations, creates seven days of future partitions, and drops a partition only when its upper bound is no later than database-now minus retention. Pair drops occur transactionally. Maximum normal-operation grace is under six hours plus five minutes, below the 24-hour requirement. The migration/deployment hook also runs maintenance. Missing partitions fail recording closed; automatic maintenance restores them. Runtime has no DDL privileges or EXECUTE permission on maintenance.

Broker startup validates the single retention duration and writes its microsecond-precision value to a singleton policy row via DML. Maintenance reads the policy under the lifecycle lock instead of parsing a second configuration format. Policy updates acquire the same exclusive lifecycle lock, so a duration increase cannot race a drop based on the old value. During a retention-setting rollout all replicas must use the same value; do not mix settings in a rolling rollout. Changed settings apply on restart. External deployments install an equivalent five-minute scheduler as part of deployment, not a manual retention procedure.

Every recording transaction, emitter, and eraser acquires a shared lifecycle advisory transaction lock first. Recorders and emitters then take shared per-subject locks; erasure takes the exclusive lock for the exact subject. Maintenance takes the exclusive lifecycle lock and no subject locks. Use distinct two-int advisory key classes for lifecycle and subject; hash collisions only serialize unrelated subjects, and SQL predicates always compare the exact principal. For operations affecting several principals, acquire subject locks in deterministic order before business row locks. Only then acquire business rows and delivery references. An emitter may read candidate identifiers optimistically, but must recheck row existence after acquiring barriers, then hold them through synchronous export and acknowledgement.

Erasure uses one operator-authorized SQL function/transaction, removes pending references and events across all partitions, and returns only a deletion count. Its completion boundary is commit under the exclusive subject lock. Writers that commit before that boundary are deleted; blocked writers commit after it as new occurrences. No event marking erasure is inserted for the erased subject. Already handed-off network/collector copies are external observability data; deletion cannot retract them. No buffered SDK copy remains available for a later send.

**Alternatives considered**: Daily partitions plus a periodic sweep can exceed 24 hours. Row-by-row retention violates FR-005. pg_partman adds an extension without necessity. A DEFAULT partition requires relocation or row deletion and hides missing maintenance. Snapshot-only erasure fails against concurrent inserts. Runtime partition DDL conflicts with accepted ADR 009.

**Primary documentation**: [PostgreSQL 17 partitioning](https://www.postgresql.org/docs/17/ddl-partitioning.html), [advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS).

## 7. Producer ownership and less obvious transitions

The complete map is in `contracts/producers.md`. Verified high-risk seams:

- `consent.Service.GrantConsent` has an explicit unchanged-state return; both revocation paths must converge on one recorded transition without changing their distinct 404/idempotent HTTP behavior.
- `approval.Service.CreatePendingApproval` distinguishes new versus returned-existing; ConsumeApproval has an already-consumed success return. Sync increments are transactional; local broadcasts must wait for outer commit.
- `oauth2session.createSession` upserts both first establishment and reauthorization. A callback establishing usable credentials is `session-established`; refresh-token operations are `session-refreshed`. A shared upsert alone cannot classify the event.
- `oauth2server.Provider` exposes client-credentials, authorization-code, and refresh issuance; Fosite's transaction boundaries must be joined to the outer operation. Proxy strategy currently streams responses when multi-agent verification is absent: stage the response, record its broker outcome, then forward. Do not parse upstream tokens merely to invent a subject.
- Credential generation/rotation/revocation currently bypasses a domain service in `client_credentials_handler.go:97-123,214`. Move that policy into the existing OAuth2-server bounded context, retaining handler logs and response contracts.
- `impersonation.evaluateRule` currently combines permission decision and minting. Record a granted decision after authorization and delegation succeed, before minting; mint failure then produces token request failure, not a false denial. Successful RFC 8693 impersonation produces `token-exchanged`, never `token-issued`.
- `SigningKeyService.PromoteKey`, `generateAndStore(makeCurrent=true)`, and bootstrap all select a current signing key. Record the committed current-key selection once; retain `data.activates_at` to distinguish selection from eligibility after the existing JWKS grace interval. Do not add an activation scheduler or modify key grace rules.
- Agent/provider deletion cascades may remove catalogued grants, credentials, approvals or sessions. Capture the actually affected rows and record their corresponding terminal facts in the same transaction; never allow a database cascade to erase ledger history. Revocation of an approval is not additionally a new user denial just because its stored status becomes denied.
- Expiration recognition needs durable `expiration_recorded_for` instants on the owning grant/approval rows, not ledger-only deduplication. Compare the marker with effective expiry; changing validity can create a new lifecycle. Repeated discovery after ledger erasure must not recreate an old occurrence. Existing lazy reads, filtered queries, duplicate retirement, and cleanup must all use this recognition seam; no wall-clock expiration scheduler is introduced.

## 8. Performance evidence and governance

**Decision**: Reuse pinned dependencies and existing Ginkgo/Go/PostgreSQL harnesses. Establish a reproducible reference profile and an operator-supplied deployment profile before release: see `quickstart.md`. Record baseline and enabled latency distributions; do not infer p99 from a mean or from a single-event microbenchmark. Target added transaction p99 <=5 ms and preserve all safety checks. No production disable switch is added merely to benchmark; compare the pre-feature binary with the implemented binary under equivalent conditions.

**Alternatives considered**: A guessed current-load number is not evidence. A production bypass would undermine mandatory recording. Timing the asynchronous collector as part of recording would measure the wrong boundary.

Initial and post-design gates: no departure from accepted storage, configuration, typed-ID, migration, or provider ADRs is selected. A new proposed ledger ADR records the cross-cutting decision; it does not make itself binding or approve a public API change. ADR 033 remains Proposed and is not silently promoted. Domain/schema publication, real migration tests, red E2E evidence, deployment configuration, and operator documentation remain explicit implementation prerequisites.
